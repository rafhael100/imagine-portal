# F389 — Actual Worker F386/F387 signature to real restricted Portal PostgreSQL18 retry

This closes the **separate-fixture gap** between F387 (actual independent Worker code but simulated local database) and F388 (real PostgreSQL18 restricted adapter with an in-process synthetic signed receipt). No operational Cloudflare instance or Portal login is introduced.

1. In a disposable PostgreSQL18 Docker cluster, the existing Portal identity provisioning code creates a genuinely active, business-shaped session using real restricted SQL roles, with an ephemeral 256-bit opaque reference. Only the isolated UID82 process can read the reference, stored in a mode-0600 scratch file.
2. A **separate network-disabled Node24 container** with UID82 executes the **actual Worker F376**, including F386's HMAC-authenticated append-only D1-style atomic intent and F387's HMAC/nonce-authenticated Ed25519 readback, against its own real in-memory SQLite database. Organization and hashed session reference come from the PG18 fixture; it never writes the raw reference to the receipt or logs. This produces a verified signed receipt with status exactly pending_local_reconciliation.
3. A fresh PHP process then verifies the actual JavaScript-signed Ed25519 bytes using the Portal's F387 verifier, binds the exact session digest and intent ID to the server-side PG18 reference, and calls F388's real SQL revoke retry candidate. It proves that invalid signature, nonce or intent cannot mutate the database.
4. A CI-only PostgreSQL trigger forces the actual restricted Portal revoke function to fail. The receipt remains valid, but SQL session remains active and F388 returns a negative outcome. Removing the trigger and repeating the signed intent successfully writes status revoked in PG18. All results are **NO SERVING**.

The PostgreSQL server and Node Worker are both under ONE disposable GitHub-hosted CI runner and shared test tenancy; this is cross-process and cross-technology integration, **not** proof of an operational independent administrative trust domain. No remote HTTPS communication is used in F389; F380 covers TLS read-only transport separately. F389 does not solve delivery/retry queues, privilege isolation in a real D1, externally protected Ed25519 private key, secure key rotation, audit/retention, HA, sustained load, no-rollback cloud backups, race-free HTTP resource fencing or disaster recovery.

No public routes, merges to main, real Cloudflare/D1, Leaseweb VPS, billing, domain changes or customers; all credentials, signatures, SQL and databases are synthetic/ephemeral. Security issue #64 is still OPEN and NO-GO.
