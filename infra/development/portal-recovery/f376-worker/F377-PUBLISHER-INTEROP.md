# F377 — Candidate PHP publisher to F376 independent witness (NO DEPLOY)

This increment implements a **dormant** Laravel Infrastructure class, `PinnedHttpsWitnessPublisherCandidate`, that sends the exact F376 witness-first publish contract over independently pinned TLS. It does not bind to routes, session/membership transactions or the production application container. All results, including successful HTTP 204 CAS, explicitly report **NO SERVING**.

The method takes a short-lived, separately controlled base64 HMAC publisher secret **per invocation**, not in constructor state, and a server-pinned organization + recovery instance. Its canonical signature covers domain-separated POST, path, Unix timestamp and the exact strict-field JSON body. It uses HTTPS, TLS chain/hostname and SHA256 SPKI validation, disables proxies/redirects and reuse, limits network time and response size, and rejects input outside the positive 1-billion bound. HTTP 409 is a non-authorizing conflict, while 204 is an equally non-authorizing lab observation. Other statuses, unavailable certificates and transport errors are sanitized as failures.

A GitHub-hosted regression creates a disposable TLS certificate and launches the **actual F376 Worker source code** through a Node.js HTTPS fixture, with an actual SQLite schema and D1-compatible adapter. PHP 8.3 and 8.4 submit HMAC-authenticated updates to that Worker via real TLS. Tests require CAS 12→13→14, replay refusal, floors never decreasing, wrong publisher secret, cross-scope refusal, incorrect SPKI, malformed endpoint inputs and verification of the resulting **Ed25519 receipt** by the real Portal F369 verifier. No user secrets or live accounts are involved.

This CI does **not** prove Cloudflare D1 remote semantics, durable independent authority, production writer credential custody, cross-store transactional consistency or on-request authorization fencing. Static TLS pinning may be incompatible with Cloudflare-managed edge certificate rotation; no real remote endpoint or Cloudflare resources are selected. A successful publish is deliberately not equivalent to permission to commit/serve the local Portal. No SSH, VPS, DNS, main merge, spending, production release or external account action. Portal issue #64 remains OPEN/NO-GO.
