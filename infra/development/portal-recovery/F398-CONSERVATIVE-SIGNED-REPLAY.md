# F398 — Conservative, bounded replay of signed independent revocation intents

F396 combines signed F392 cursor receipts with signed F395 retry leases and F393 ACK claims, and refuses skipping the restricted PostgreSQL status read. F397 independently verifies the same policy against the **real disposable PostgreSQL18** role. An additional operational risk remains: a worker that remembers a cursor in memory could crash and mistakenly assume earlier work was completed. A signed *empty* cursor page can never imply all previously observed intents have been reconciled.

F398 introduces a **dormant read-only** `ConservativeSignedRevocationScanCandidate` that accepts at most 16 pre-fetched independent signed pages and a trusted current clock. It does not open the network, persist a checkpoint, perform SQL writes, acquire leases, publish ACKs, schedule work, or authorize HTTP.

Each page is verified through the existing F396 policy: current Ed25519 cursor challenge, server-pinned organization and witness signer, matching F395 lease nonce/digest/sequence and optional F393 signed ACK. Critically, the candidate only **advances a volatile cursor** to the next signed sequence if BOTH the independent ACK is signed AND the *restricted PostgreSQL diagnostic* returns a revoked row. A still-active row with an ACK (including a forged claim from the actual Worker) returns an unresolved stop, not progress. Without ACK, the scan stops even if SQL says revoked. A missing row, expired lease, invalid signature, incorrect sequence or incomplete input stops immediately. A valid signed empty page returns `SCAN_SIGNED_EMPTY_NOT_QUEUE_COMPLETE`, with every authority flag false.

After a crash, there is deliberately no persisted cursor: the candidate replays from sequence 0, revalidating the latest SQL state for each intent. The `verifiedLocalRowsObserved` and `lastVolatileObservedSequence` fields are **diagnostic counters only**. `isDurableCheckpoint=false` ALWAYS. Never use those counters to clean up independent records or release HTTP/permissions.

A PHP process with a negative-only synthetic SQL status interface checks halt-on-ACK-conflict, no-ACK halt, restart re-scan, tampered cursor/lease/ACK, duplicate cursor, empty page, invalid input, 16 page cap and missing/expired rows. F397's real PG18 adapter contract remains the reference for actual SQL behavior; F398's policy test uses synthetic status to isolate the control flow.
