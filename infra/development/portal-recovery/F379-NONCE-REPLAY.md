# F379 — Nonce-bound Ed25519 witness receipt prevents signed replay within TTL

The earlier F368/F369 witness receipt is signed and short-lived, but a previously issued V1 response can remain cryptographically valid for up to 60 seconds. If a recovery process accepts a stale cached V1 statement, it could be tricked into comparing it against an old PostgreSQL snapshot even though the real independent witness has already advanced. F371's two reads are **not sufficient** when both reads receive the same replayed receipt.

F379 adds a **new, opt-in, dormant v2** path on the standalone Worker prototype: `GET /v2/portal/recovery-witness`. It requires the request header `X-Imagine-Witness-Nonce` to be **exactly 64 lowercase hex characters, generated from fresh 32-byte cryptographic randomness for every request**. The Worker signs the nonce together with tenant scope, instance, generation/session/membership floors, monotonic sequence, issued timestamp and 30-second expiry using a distinct Ed25519 signature domain and v2 schema. There are no URL/query/body-supplied tenancy or sequence selectors. Response disables caching; missing/malformed nonce is rejected. The older V1 path remains for laboratory compatibility but **MUST NOT** be used for future serving.

The Portal-side **candidate** `ChallengeBoundWitnessCandidateVerifier` validates strict ordered keys, separately pinned signing public key, expected per-request nonce, Ed25519 signature, time window, organization/instance and exact revision vector. It rejects an old signed response with a different challenge even if its signature and expiry would otherwise be valid. Returning `WITNESS_MATCHED_STILL_NO_SERVING` is still a **negative-only diagnostic**, and all HTTP/session/business/deploy flags remain false.

## Verification

GitHub-hosted Node 24 executes the actual F376 Worker module with an in-memory SQLite D1-compatible adapter. It captures two Ed25519 receipts before and after advancing the independent sequence via HMAC-authenticated Worker POST. A separate PHP 8.3/8.4 process verifies the resulting signed bytes using the real Portal F379 candidate. Tested: first/second fresh 256-bit nonce, replay of old signed reply against new nonce, old epoch against current witness, tampered nonce/signature/sequence, swapped organization, unsigned V1 response, malformed body, missing nonce and expiry/future clock. Only synthetic credentials and data are used; no Cloudflare resources.

**Still blocking (#64):** No operational remote transport issuing cryptographically fresh nonces, no externally controlled signing/monotonic authority, no forced online challenge on each authorization path, no safe revocation across hosts, no distributed atomicity, privileged-operator protection, persistent anti-rollback storage, mTLS/credentials, race-free gateway fencing or recovery approval. A challenge protects against reusing an **old signed response**; it does **not** protect against a genuinely compromised or rolled-back signing service that signs incorrect data. No VPS, main, domain, deploy, customer data or new expense is involved.
