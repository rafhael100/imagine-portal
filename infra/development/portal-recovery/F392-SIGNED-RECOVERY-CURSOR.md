# F392 — HMAC-authenticated Ed25519 recovery cursor over append-only revocation intents

F386 stores independent immutable revocation intents; F387 allows readback only when the worker already knows a specific 128-bit `intent_id`. After a Portal crash, that ID might be lost, and simply enumerating a local PostgreSQL outbox may be impossible if that DB itself is unavailable. F390/F391 can reconcile a digest and prove SQL row status, but they still need to *discover the independent intent to process*.

F392 introduces a **DORMANT recovery cursor** on the independent Worker F376 candidate. It returns **exactly one next append-only intent** by monotonic `to_sequence`, never a public list or a login/bearer.

- The new GET path is `/v1/portal/revocation-intents/next`. It precedes the F387 per-ID route. The server *never* accepts an organization or instance from browser/query parameters; those are pinned by operator-controlled bindings.
- It requires a **separate** 32-byte HMAC key `INTENT_CURSOR_HMAC_B64`, distinct from the publisher secret used to append intents. It authenticates method `GET`, the fixed path, timestamp (30 seconds), fresh caller nonce (32 random bytes / 64 lowercase hex) and canonical `X-Imagine-After-Sequence` (no leading zeros; 0–1,000,000,000). Anonymous/invalid requests are denied before any data read.
- It reads the current witnessed sequence and session floor and the **oldest** matching intent with `to_sequence > after_sequence`. A new candidate D1 index on `(organization,instance,to_sequence)` avoids full scans as append-only history grows. A row ahead of the current witness is denied.
- It signs a **short-lived Ed25519** receipt containing the tenant, original cursor, current witness sequence/floor, immutable intent ID and SHA256 session digest, intent sequence/floor, nonce, issued/expires and exact status `pending_local_reconciliation`. When no row exists after the cursor, it signs `no_intent_after_cursor` with empty ID/hash and zero intent sequence; this NEVER proves that earlier intents were processed.
- `SignedRevocationCursorCandidateVerifier` on the Portal PHP side enforces the exact ordered JSON schema, independent pinned public key, nonce, cursor, tenant, monotonicity, TTL and signature. Both pending and empty responses have all HTTP/business/session/restore/deploy, `canClaimPostgresRevoked` and `canClaimQueueFullyProcessed` flags **FALSE**.

## Recovery behavior, limitations, verification

A safe *laboratory* restart can begin at sequence 0 and rediscover the same intents, then fetch each F387 signed per-ID readback and use F391's restricted digest-only SQL reconciliation. **Idempotent reprocessing** is preferable to losing revocations when local state is uncertain. F392 does **NOT** provide a durable checkpoint, claim/lease, completion ACK, a tamper-resistant global queue, automatic worker, or proof of all pending work processed. Returning an empty page after a cursor can never authorize the Portal, or justify deleting earlier records.

GitHub CI Node24 uses the real F376/F386/F392 Worker modules with ephemeral HMAC/Ed25519 keys, in-memory SQLite with actual append-only SQL triggers and a candidate cursor index. It appends two intents (sequence 12→13→14), tests oldest-first enumeration, restart from zero, signed empty proof, nonce freshness, HMAC separation, wrong cursor/invalid key/timestamp, strict no query parameters, and force-injected witness rollback. Separate PHP 8.3 and 8.4 verify exact Worker Ed25519 signatures for first, second and empty receipts, and reject forged, stale, incorrectly scoped or noncanonical data. Existing F376 protocol tests are rerun as regression.

This is NOT a live Cloudflare D1 deployment, independent administrative trust host, anti-rollback proof against D1 superuser, worker scheduling, queue exhaustion proof, production TLS/secret rotation, signed PostgreSQL ACK, full RLS tenant isolation or race-free authorization. It exposes no Laravel route/DI binding, and no public-serving decision. No VPS, domain, real users, main merge, SQL production migration or cost. Security issue #64 remains OPEN/NO-GO.
