# F397 — Actual restricted PostgreSQL18 conflicts with signed revocation ACK claims

F396's negative-only recovery triage used the actual independent Worker code F376/F386/F392/F393/F395 and Ed25519 receipts, but a synthetic PHP status adapter. F397 replaces that adapter in the *integration test* with the **real restricted Portal PostgreSQL18 runtime role**, leaving every authorization and queue-complete flag false.

The F390 seed script creates a genuine business-shaped active session in a disposable PG18 database and discards the original bearer before writing a protected fixture containing only tenant UUID and SHA256 digest. F391's security-definer status SQL is installed explicitly in this disposable cluster; **it is not part of live Laravel migrations**. The isolated network-disabled Node24 container uses this same tenant and digest to generate actual F392 signed cursor, F395 active/expired/exhausted leases, and an intentionally dishonest but valid F393 signed ACK claim. Thus the independent witness can say "ACK recorded" while real PG18 is **still active**.

A separate PHP process invokes `SignedRevocationRecoveryTriageCandidate` backed by **real `PostgresPortalBrowserAuthentication`** with its HMAC-scoped role. A signed ACK with active PG18 must return `ACK_CLAIM_CONTRADICTS_ACTIVE_POSTGRES`. The candidate cannot query SQL without valid signed cursor+lease, but an ACK never skips SQL. Invalid signatures are blocked, an expired lease is never treated as active, exhausted retries escalate. SQL UPDATE failure is induced by a CI-only trigger; the session remains active. After the fault is removed and the same PG18 runtime HMAC revoke function executes, status becomes revoked, yet both signed ACK and absent ACK results remain **NO SERVING**. A signed empty cursor never certifies queue completion.

Both Worker code and PG18 are tested with actual crypto and real SQL inside one GitHub runner, not in independent administrative control planes. F397 does not install a scheduler or operational queue, does not prove off-host D1 administrator/backup rollback safety, key rotation, recovery acknowledgments, failover, tenant scalability, HTTP resource fencing or production DR.
