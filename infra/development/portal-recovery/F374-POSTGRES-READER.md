# F374 — Actual local PostgreSQL epoch source, external witness transport unimplemented

Following the F373 quarantine-only local schema, F374 adds a server-scoped, **read-only real PostgreSQL** source class: `PostgresPortalRecoveryEpochCandidateReader`. It enforces the dedicated `portal_recovery_epoch_reader` role, PostgreSQL driver and expected database, absence of a caller-owned transaction, role safety flags, FORCE RLS, no write privileges and a **server-pinned organization UUID and recovery instance**. Every invocation fetches the current quarantined row; no result is cached and no browser-supplied tenant selector is accepted by the class.

`LiveRecoveryWitnessSourceCandidate` composes that local PostgreSQL read with `IndependentSignedWitnessTransport`, a **contract with deliberately no operational implementation**. It can feed F371/F369's per-read signed witness checks without conflating local and independent trust domains. The Portal still has no network client, signing provider, witness key vault, session issuer/serving fence or app binding.

In disposable CI, the PostgreSQL 18 runner installs F373's migration only after provisioning the authentic Portal identity foundation. For testing only, a PostgreSQL administrator temporarily `SET ROLE`s the **NOLOGIN** recovery reader, and an in-memory simulated independent source returns an ephemeral Ed25519 attestation. The test demonstrates a correct read of the real epoch table, stale local or remote sequence denial, signature failure, remote outage and immediate denial when the PostgreSQL connection changes role, with all authorization flags false. This is **not** a route or production read-only service.

**Known limits:** The NOLOGIN reader policy currently sees all epoch rows when a trusted DBA exercises it with SET ROLE; cross-tenant secrecy would need a properly scoped independently authenticated runtime principal **before ever allowing LOGIN**. The local epoch itself is subject to restore rollback. A matching independent witness is still insufficient without a mandatory always-on serving fence and cross-system revocation protocol. No migration was installed on the Leaseweb VPS; no main merge, deployment, customer data, DNS change, external key service or production approval. Issue #64 remains OPEN/NO-GO.
