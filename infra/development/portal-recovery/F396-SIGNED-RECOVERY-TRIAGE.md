# F396 — Fail-closed decision policy: signed cursor + lease + ACK + SQL

F392 can enumerate independent immutable revocation intents after crashes. F395 can coordinate no-more-than-one active, short-lived retry lease and preserves its bounded attempts after worker restart. F393/F394 create ACK **claims** after a restricted PostgreSQL status read in the lab. A danger remained: a developer could mistakenly treat the *presence* of a signed ACK or an empty cursor page as sufficient proof to mark an independent intent completed and skip further SQL reconciliation.

F396 introduces a **pure, read-only** `SignedRevocationRecoveryTriageCandidate` without HTTP bindings, network side effects, queue writes, key storage, or a scheduler. It requires the F392 signed cursor with exact caller nonce, tenant, instance, requested sequence and pinned Ed25519 signer. An empty signed page yields **NO_NEXT_INTENT_NOT_QUEUE_COMPLETE**, never a global queue-complete certificate. Pending pages require a matching F395 lease receipt whose Ed25519 signer, SHA256 session digest, intent ID, intent sequence, lease digest, nonce and timestamp match. A missing/unverified lease prevents any PostgreSQL read.

An optional F393 signed ACK receipt is checked with a *different* expected nonce but **cannot skip the PostgreSQL status read**, even when the Worker genuinely signed the ACK. The only SQL diagnostic interface is F391's `PortalHashedSessionStatusCandidate`, using the digest and server-pinned organization from the independently verified cursor. Reported states are conservative: still active + valid ACK => **ACK_CLAIM_CONTRADICTS_ACTIVE_POSTGRES**; missing row => manual escalation; database error => deny; expired lease => reacquire only after new signed claim; exhausted retry budget => manual escalation. Revoked row + ACK may be reported for diagnostic review but **can never authorize HTTP, claim global queue completion or bypass revalidation**.

CI Node24 executes the actual F376/F386/F392/F393/F395 Worker modules with ephemeral HMAC and Ed25519 keys and disposable SQLite. It produces genuine, cross-language signed receipts for active, expired and exhausted leases, a valid deliberately **false** ACK claim, and an empty cursor page. PHP 8.3/8.4 consumes the exact signature bytes in a separate process, using a synthetic restricted status adapter to exercise all decision branches and ensure invalid signatures/nonce/tenant never read PostgreSQL. Existing F391 separately proves the SQL reader works with real PostgreSQL 18, and F394 separately proves the actual Worker F393-to-PG18 flow. F396 is policy composition **not** a new end-to-end live Cloudflare/PostgreSQL deployment.

All outcomes set canAuthorizeHttp, canAuthorizeBusiness, canIssueSession, canRecoverFromRestore, canDeploy, canClaimPostgresRevoked, canClaimQueueFullyProcessed and canSkipReconciliation to **false**. Even a positive local SQL read or signed ACK could become stale after privileged restore: production still requires independent anti-rollback, clock/lease fencing, off-host keys, atomic durable queue operations, IAM/HA/DR, real migrations and AppSec/DBA review. No VPS, Cloudflare, DNS, customers, live routes, merge/main or new cost. Issue #64 stays OPEN/NO-GO.
