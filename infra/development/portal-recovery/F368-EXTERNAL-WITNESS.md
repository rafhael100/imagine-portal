# F368 — Independent PostgreSQL 18 witness of restore epoch (CI only)

This increment responds to [Portal SEC-R03 issue #64](https://github.com/rafhael100/imagine-portal/issues/64) without pretending that a matching pair of local JSON files is an authoritative recovery proof.

The workflow spins up **two independently initialized PostgreSQL 18 clusters**: Cluster A has the Portal's genuine Laravel-auth SQL, a synthetic operator and a current signed-in session. Cluster B is a **separate Docker container**, with its own database, admin secret and volume, configured with `--network none` and **no published ports**. Its state is not present in Cluster A's `pg_dump`. An unprivileged NOLOGIN read-only witness role cannot UPDATE or DELETE its protected table. A monotonic trigger refuses decreasing epoch sequences for the simulated witness.

The test takes an old dump of Cluster A while the session is valid. It **revokes the session in the live source**, advances an independently stored witness sequence from 12 to 13, restores the old dump into a third database with application roles denied CONNECT, and demonstrates that the old session would become SQL-valid **inside that inaccessible copy**. It then reads the restored revision vector from the restored database and the advanced witness vector from Cluster B; the existing `recovery_epoch_preflight.py` must report `BLOCKED` / `can_authorize_http=false` and exit 65. A real F365 quarantine is exercised against the restored copy, and must revoke the old session. With Cluster B stopped and its evidence unavailable, the preflight must again deny instead of falling back to the stale source.

**Boundaries:** This is still a CI proof, *not* an operational independent witness service. It uses a synthetic extra snapshot marker, SQL administered by the GitHub runner, and two containers under one runner host. There is **no external KMS**, durable off-host immutability, authenticated/online witness-reader protocol, atomic cross-database commitment, business workload reconciliation, Cloudflare/Laravel serving fence or key rotation; a privileged host operator could still roll back both containers. Witness policy, compromised-runner scenarios, network failures, multi-tenant support, service restart and backup disaster-recovery semantics require a separately reviewed operational design. No VPS access, no customer data, no migration or API in Laravel, no new recurring cost or production activation.

**Verdict:** `LAB_STALE_WITNESS_DETECTED_STILL_NO_SERVING` in reasoning only; no function or workflow returns GO. Portal #64 remains open and blocks public serving. Branch and PR are draft and should not be merged or deployed.
