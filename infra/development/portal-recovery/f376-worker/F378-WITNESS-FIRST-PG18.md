# F378 — Worker witness-first vs real PostgreSQL 18 old-backup replay

This is an isolated GitHub Actions rehearsal of a **specific failure window** in the Imagine Portal restoration threat model. It builds on F370's two-store ordering but replaces the simulated external PostgreSQL witness with **the exact F376 Worker logic**, running behind an actual localhost HTTPS certificate, TLS SPKI pin and Node.js SQLite D1-compatible adapter. The source auth database remains a real Docker PostgreSQL 18 with the authentic Portal SQL session functions.

The CI performs this sequence: (1) creates a synthetic authorized session in PG18, an epoch marker at sequence 12 and an old PG18 dump; (2) calls the **real PHP F377 HTTPS/HMAC publisher**, which advances the independent Worker state 12→13; (3) injects a PostgreSQL transaction error after attempting to revoke the session. The local revocation rolls back and the old session remains SQL-valid; the **signed Worker receipt correctly reports 13**, so the F369 verifier refuses the old epoch 12. (4) A new local PG18 transaction atomically revokes the session and records its local epoch 13; the matching signed witness remains **NO SERVING**, not an access authorization. (5) CI restores the old PG18 dump into a separate DB with application runtime roles denied CONNECT; the obsolete session is again SQL-valid there. F369 refuses the restored epoch; F365 post-restore quarantine then revokes the resurrected session.

The **old session remaining SQL-valid during the injected local failure is a proven danger**. The CI verification is not wired to the Portal HTTP serving pipeline; users must not infer a safe login path. The external witness source is **not** Cloudflare's remote Worker or D1 and is not durable across a runner crash. There is no production-grade off-host key custody, authenticated publisher credential service, fenced serving, cross-store atomic transaction, HA/disaster recovery, reconciliation of external tokens or key rotation. No real customer data, VPS, DNS, Cloudflare resources, deployment or spending is involved.

**Every result remains NO-GO for public serving.** F378 makes the threat and the mitigation protocol testable but does not release the Portal. Issue #64 remains OPEN pending independent security review and operational recovery controls.
