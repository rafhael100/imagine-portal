# F373 — Recovery epoch schema with permanent quarantine

This change creates an **uninstalled** Laravel PostgreSQL 18 migration for `public.portal_recovery_epoch_candidates`, one local recovery epoch vector per organization: server-controlled organization UUID, instance, generation, session/membership revision floor, and witnessed sequence. The row has exactly **one** permitted state, `quarantined`. There is **no** `ready`, `serving`, `approved` or `active` value. These local records alone NEVER grant auth, permission, recovery or deploy authority.

A trigger rejects decreasing generation/revisions/sequence, immutable organization/instance edits and skipping witness sequence numbers whenever the vector changes. FORCE RLS and explicit revocation of public table rights deny arbitrary runtime reads and writes. A proposed `portal_recovery_epoch_reader` is strictly NOLOGIN, NOINHERIT, NOSUPERUSER and SELECT-only with its own RLS SELECT policy. Neither the regular Portal browser runtime role nor envelope runtime role gets access, and no caller is permitted to update via this reader. A later approved writer/reader identity and actual independently signed witness are still required.

The dedicated PostgreSQL 18 GitHub Action provisions the real Portal auth foundation, then **runs the migration only on a fresh disposable runner** with synthetic enrollment data. The runner verifies FORCE RLS, absence of runtime grants, restricted NOLOGIN role, tenant isolation and monotonic trigger failures. It also verifies that a successful revision update cannot change `quarantined` and that rolling back a nonempty evidence table is refused.

**Not automatically installed**: the existing `infra/development/portal-db/provision.php` manifest remains unchanged, as does the `main` branch and Leaseweb VPS. The migration is for DBA/AppSec review only. No actual off-host witness, secret/key custody, serving-path enforcement, cross-database monotonic atomicity or DR approval follows from this schema; Portal issue #64 stays OPEN/NO-GO.
