# F369 — Ed25519 signature verification of independent witness epochs

F368 demonstrated that a second PostgreSQL 18 cluster can retain newer revocation state outside the Portal dump. F369 adds a dormant **Portal Infrastructure** verifier `IndependentWitnessCandidateVerifier` for a domain-separated Ed25519 attestation binding organization, recovery instance, generation, session revision floor, membership revision floor, and monotonic sequence, with strict 120-second TTL. The verifier takes a **separately pinned public key**; accepting a public key from the restored database or user request would defeat the trust boundary.

**Threats tested** in PHP 8.3 and 8.4: wrong key, tampered sequence, future/expired attestation, extra payload fields including contact data, cross-organization/instance substitution, stale or ahead-of-witness revisions, malformed signatures and unsafe numeric types. A signature-valid *matched* epoch still returns `WITNESS_MATCHED_STILL_NO_SERVING`, never GO. Stale restore returns `WITNESS_RESTORED_EPOCH_CONFLICT` even with a properly signed witness. Every result has false authorization flags.

The GitHub F368 workflow also reads the actual epoch vector from the restored Portal DB and the current vector from the **independently initialized** witness cluster, creates a disposable Ed25519 attestation in the GitHub-hosted harness (outside the restored DB snapshot) and exercises the real candidate verifier, including tampering refusal. The CI-only signing code remains entirely in `infra/development/portal-recovery/test-f369.php` and is **NOT** an authorized production witness signer.

**Still missing** before operational activation: trusted private signing service and key custody on a genuinely independent host, publisher access control, authenticated collection, key ID/rotation and revocation, witness high availability and monotonic durability across backups, two-phase cross-store consistency, serving-side mandatory checks without caching bypass, network partition handling, disaster recovery, privileged operator review and AppSec/DBA approval. This PR creates no public route, migration, user session, deployment or external vendor expense. Portal issue #64 remains **OPEN/NO-GO**.
